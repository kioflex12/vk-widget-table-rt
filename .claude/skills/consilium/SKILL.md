# Задача
Прогнать гипотезу/рекомендацию через консилиум advisor'ов ДО выдачи пользователю. Если консилиум отверг — НЕ выдавать рекомендацию, честно сказать «проверил, гипотеза не выдержала разбор».

Гипотеза/рекомендация для проверки: **$ARGUMENTS**

## Когда запускать
- Диагноз бага («виджет не обновляется, потому что X»), выбор подхода («хранить данные так, а не эдак»), нетривиальное изменение архитектуры (авто-заполнение таблицы, новый источник данных, смена auth-флоу).
- НЕ запускать для фактологии («что делает функция parseCsv?»), для просьб «дай код», для уточняющих вопросов. Это дорого и бессмысленно.

## Шаги

### 1. Сформулируй гипотезу строго
Перепиши гипотезу в 1-2 предложениях с конкретикой: какая причина / какой фикс предлагается, и **на каких уликах** основано (`file:line`, коммиты, поведение в браузере, ответ VK API).

Если **улик нет** или они слабые — НЕ запускай consilium. Сразу скажи: «недостаточно данных для гипотезы, не буду спекулировать». Это лучше, чем тратить консилиум на пустоту.

### 2. Выбери состав консилиума

**Обязательны всегда** (2 + gate):
- `advisor-skeptic` — ищет дыры, контр-доказательства, edge-cases (пустой CSV, битые ссылки, отсутствие group_id, XSS из ячеек).
- `advisor-engineer` — проверяет техническую правдоподобность по **реальному коду** (`app.js`, `index.html`, VK Bridge API).
- **quality-gate** — оценивает предлагаемое решение по [quality-rubric.md](quality-rubric.md). Срабатывает КАЖДЫЙ прогон без исключений.

**По релевантности** (опционально):
- `advisor-pragmatist` — если про scope/MVP/«что самое дешёвое, что решит проблему», «стоит ли вообще это делать сейчас».
- `advisor-user-advocate` — если про UX (что видит игрок в таблице/виджете, что видит админ в панели, мобилка, локаль).
- `advisor-visionary` — если про долгосрочные последствия / lock-in (смена источника данных, auth, зависимость от Google Sheets / VK API).

### 3. Spawn'ни advisor'ов **параллельно** (одним сообщением, несколько `Agent` tool calls)

Каждому advisor'у в его initial prompt включи:
- **Исходный вопрос пользователя** целиком.
- **Гипотезу/рекомендацию, которую проверяешь** (1-2 предложения).
- **Что уже проверено в коде** — конкретные цитаты `file:line`, не пересказ.
- **Явную фразу**: «У тебя есть доступ к коду проекта через Read/Grep/Glob и git (Bash `git log/show/diff`). Проект маленький — `app.js`, `index.html`, `styles.css`. Если данных в этом prompt недостаточно для verdict'а — дочитай код сам, не угадывай. Если после этого всё равно не хватает — скажи "недостаточно контекста для verdict'а" вместо BLOCK/CLEAR. Внешние факты (VK Bridge API, Google Sheets API, gspread) при необходимости проверяй через WebFetch/WebSearch.»

**quality-gate агент** (спавни тем же сообщением, параллельно): оценить предлагаемое решение СТРОГО по [quality-rubric.md](quality-rubric.md). В prompt включи: полный текст рубрики (или путь к файлу), конкретный diff/решение целиком, исходный вопрос, и требования: «суди по логике изменения, не по комментариям; символы (функции, DOM id из `getElementById`, поля) проверяй grep'ом по реальному коду, не по памяти; верни per-пункт verdict (block/worry/ok) + итоговый gate-verdict». Для снятия self-bias запускай его на другой модели (`model: 'sonnet'`).

### 4. Дождись всех verdict'ов и синтезируй

| Сценарий | Действие |
|---|---|
| Хотя бы 1 advisor сказал BLOCK / WORRY / DEAD-END / INFEASIBLE с **конкретной evidence** | Гипотезу НЕ выдавать. Написать: «проверил гипотезу X через consilium — отверг, причина: Y (цитата advisor'а)» |
| Хотя бы 1 сказал «недостаточно контекста» | Гипотеза слабая. Не выдавать. Сказать: «нужно больше данных для проверки» |
| Все CLEAR / OK-WITH-CAVEATS / SOLID / SHIP-AS-IS | Выдать рекомендацию с пометкой **«[проверено consilium]»** + 1-2 строки от каждого advisor'а |
| Mixed CLEAR + WORRY-with-caveats | Выдать с явным блоком caveats: «consilium советует, но обратите внимание на: ...» |

**Quality-gate имеет право вето независимо от advisor'ов.** Если gate вернул `block` хотя бы по одному пункту рубрики — решение НЕ выдавать, даже если skeptic/engineer сказали CLEAR (это разные оси: advisor'ы проверяют правдоподобность гипотезы, gate — качество самого решения). Verdict gate'а **всегда** показывай в итоге одной-двумя строками: какие пункты рубрики ok / worry / block.

### 5. Никогда
- НЕ выдавай вывод консилиума как факт. Это **взвешенное мнение** на базе кода, не оракул.
- НЕ запускай консилиум для фактологии/уточнений/«дай код».
- НЕ предлагай слабую альтернативу «чтобы что-то сказать», если консилиум отверг основную гипотезу. Лучше «не нашёл достаточных оснований для рекомендации».

## Anti-patterns
- ❌ Прогон «для галочки» на очевидной фактологии.
- ❌ Spawn только одного advisor'а — это не консилиум, а одинокое мнение.
- ❌ Игнор WORRY/BLOCK от одного advisor'а потому что «остальные ОК».
- ❌ Перефраз советов в свои слова без указания, что это вывод консилиума.
